# Pruebas — Wanchaq Limpio

> Registro vivo de todas las pruebas automatizadas del proyecto: qué verifica cada una y a qué requisito o dimensión de la matriz de operacionalización (Anexo 2) se conecta. Se actualiza cada vez que se agregan, modifican o eliminan pruebas — es evidencia directa de verificación para la tesis, no solo un detalle técnico. El estándar de qué pruebas son obligatorias por módulo vive en [`plan.md`](./plan.md) §1.5.

## Cómo ejecutar las pruebas

```bash
# Unitarias (JVM, incluye Robolectric donde haga falta)
./gradlew testDebugUnitTest

# De UI / instrumentadas (requieren emulador o dispositivo conectado)
./gradlew connectedDebugAndroidTest

# Todo junto con lint y compilación, tal como se verifica antes de cada commit
./gradlew assembleDebug assembleDebugAndroidTest ktlintCheck detekt testDebugUnitTest
```

Backend (Django, carpeta `backend/`; ver [`despliegue.md`](./despliegue.md) §3 para crear el entorno virtual):

```powershell
cd backend
.\.venv\Scripts\python.exe manage.py test
```

No usan red ni claves, y **nunca leen tu `.env` ni tocan la base real** (`manage.py test` usa `settings_test.py`: SQLite en memoria).

## Notas técnicas de testing (para no repetir diagnósticos)

### DataStore + JVM unit test + Windows → usar Robolectric

Cualquier prueba unitaria que haga una **segunda escritura** sobre el mismo `DataStore<Preferences>` real (no mockeado) debe anotarse con `@RunWith(RobolectricTestRunner::class)`. Sin eso, `android.os.Build.VERSION.SDK_INT` vale `0` en un test JVM puro, DataStore internamente cae en el `File.renameTo()` heredado (en vez de `Files.move()`), y en Windows esa función **falla silenciosamente si el archivo destino ya existe** — la primera escritura funciona (el archivo no existe aún), la segunda falla siempre, de forma determinística. No es una condición de carrera y no se arregla con delays ni cambiando el dispatcher (se probaron y descartaron ambos). Ver `app/src/test/java/com/wanchaqlimpio/app/data/repository/ConsentimientoRepositoryImplTest.kt` para el patrón a replicar, y `app/build.gradle.kts` (`testOptions.unitTests.all.jvmArgs`) para los flags `--add-opens` que Robolectric necesita en JDK 17+/21.

### Compose UI Testing sin Hilt

Las pantallas se separan en un composable "stateless" (recibe callbacks simples, sin `hiltViewModel()`) y un wrapper delgado que sí conecta el ViewModel — así las pruebas de UI no necesitan levantar infraestructura de testing de Hilt (`HiltAndroidRule`, `@HiltAndroidTest`, etc.). Ver `OnboardingContent` (testeable) vs. `OnboardingScreen` (wrapper) como ejemplo a replicar en las próximas pantallas.

### Gradle: `BUILD FAILED` con `TimeoutException` aunque todas las tareas pasaron

Observado el 2026-09-19 (Gradle 9.4.1, Windows, equipo con carga): tras terminar bien `testDebugUnitTest`, `ktlintCheck`, `detekt` y `assembleDebug`, Gradle escribió «Problems-report is taking too long to write…» y cerró con `BUILD FAILED … java.util.concurrent.TimeoutException (no error message)`. Es el **informe de problemas** de Gradle (experimental, `build/reports/problems/`), no el código: los resultados de las 172 pruebas mostraban 0 fallos y repetir el mismo comando dio `BUILD SUCCESSFUL` (todo `UP-TO-DATE`). Las corridas siguientes usaron `--no-problems-report` (opción que figura en `./gradlew --help`) y no lo repitieron. Si vuelve a pasar, **mirar primero si alguna tarea dice `FAILED`** antes de sospechar del código.

### Robolectric con gráficos nativos en Windows: `BitmapFactory.decodeFile` deja el archivo abierto

Observado el 2026-09-19: las pruebas de `reducirFotoEnDisco` (que **reemplaza** la foto por su versión reducida) fallaban **solo en Windows** con `FileSystemException … El proceso no tiene acceso al archivo porque está siendo utilizado por otro proceso`. Se probó **paso por paso** (una prueba de diagnóstico que, tras cada operación, intentaba mover el archivo): `BitmapFactory.decodeFile(ruta, …)` lo dejaba bloqueado **para siempre** con `@GraphicsMode(NATIVE)`; `decodeStream(flujo propio)`, con o sin búfer, y `decodeByteArray` **no**. Como en Windows un archivo abierto no se puede borrar ni reemplazar (en Linux y Android sí), el código de producción decodifica ahora con `decodificarArchivo` (flujo propio, cerrado siempre). **Antes de esto se descartaron dos causas que parecían obvias**: `File.renameTo` (en este JDK sí reemplaza un archivo existente; se comprobó con un programa aparte) y `ExifInterface(ruta)` (se cambió y siguió fallando; se revirtió). Moraleja: en pruebas que reemplazan archivos, no usar `decodeFile`; y ante un bloqueo de archivo, **medir en qué paso ocurre** antes de suponer.

### Inicialización de WorkManager con la fábrica de Hilt (hallazgo del 2026-09-19)

| Archivo | Caso de prueba | Qué verifica | Requisito / dimensión relacionada |
|---|---|---|---|
| `InicializacionWorkManagerTest.kt` (2, Robolectric) | el **manifiesto fusionado** no trae `androidx.work.WorkManagerInitializer` (y los demás inicializadores de `androidx.startup` siguen) · `WorkManager` arranca con la configuración de la aplicación, es decir, con la **fábrica de Hilt** | Que `SyncWorker` y `EliminarReporteWorker` (`@HiltWorker`) se puedan crear en un dispositivo real | RF-03, RNF-01 |

**Un fallo real, anterior al mapa, que nadie había visto**: `WanchaqLimpioApp` implementa `Configuration.Provider` (entrega la fábrica de Hilt), pero el manifiesto seguía instalando el inicializador automático de WorkManager. La documentación de Android dice que ese inicializador **hay que quitarlo** para que se use la configuración propia («debes quitar el inicializador por defecto para que tu `getWorkManagerConfiguration()` surta efecto»), y el código de `work-runtime` 2.11.2 lo confirma: se desensambló `WorkManagerInitializer.create` y llama a `WorkManager.initialize(context, Configuration.Builder().build())`, es decir, la configuración **por defecto**. Con la fábrica por defecto, un trabajo `@HiltWorker` (su constructor recibe dependencias) no se puede crear, así que **la sincronización habría fallado en un dispositivo real**. No se había visto porque `SyncWorkerTest` construye los trabajos con su propia fábrica y **la sincronización nunca se ejecutó en un dispositivo** (tarea D9 del tablero). Lo delató el **error fatal de lint de `release`** (`RemoveWorkManagerInitializer`) al compilar por primera vez esa variante con los seguros satisfechos (hasta ahora no podía completarse: faltaba `contactEmail`, tarea E1), no una prueba.

Se escribió primero la prueba del manifiesto y **falló** (`inicializadores presentes: [androidx.work.WorkManagerInitializer, okhttp3…, androidx.emoji2…, …]`); se quitó el inicializador (`tools:node="remove"` en `AndroidManifest.xml`) y **pasó**. **Límite, dicho sin rodeos**: la segunda prueba **no** habría detectado el problema (pasaba también antes del arreglo) porque Robolectric no ejecuta el inicializador automático de `androidx.startup`; vigila otra cosa (que la configuración de la aplicación siga trayendo la fábrica de Hilt). **No verificado**: que en un dispositivo real el trabajo se cree y el reporte pase a «Enviado» (escenario C10 de [`prueba-en-dispositivo.md`](./prueba-en-dispositivo.md)).
